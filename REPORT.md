# adler2 2.0.1: verification status report

## Summary 

Specs and proofs generated by Claude verify 13 of the crate's 14 functions, including the
vectorised, deferred-modulo core (`compute`) against the textbook per-byte definition from RFC 1950.
The one unverified function is `adler32<R: BufRead>`, a 12-line loop over a generic reader that
vstd has no model for. The trusted base is 3 specifications of std's `ChunksExact` (`chunks_exact`,
`remainder`, `next`) plus the 3 uninterpreted functions that model it; `verus --no-cheating` flags
exactly those. A runtime test checks that model against the real standard library. No upstream bug
was found. One documentation gap: `from_checksum` accepts values that are not Adler-32 checksums,
and such an instance changes value on its first `write_slice` even when the slice is empty
(`0xFFFF_FFFF` → `0x000E_000E`); the docs say nothing about non-checksum inputs. The proof also
machine-checks the source comment's claim that 5552 groups per chunk cannot overflow `u32`, for
every starting state the type allows; 5553 is rejected.

A hand-written gold spec of the public API 
was compared with Claude's spec as Verus refinement obligations in both directions, with Claude
writing the linking proofs. The two specs cover 7 functions in common (`new`, `default`,
`from_checksum`, `checksum`, `finish`, `write_slice`/`write`, `adler32_slice`). Claude's spec
implies the gold spec for 6 of 7, and the gold spec implies Claude's for 6 of 7. The exception,
in both directions, is `write_slice` on a state restored by `from_checksum` from a value that is
not an Adler-32 checksum: the gold spec (a natural reading of the docs) says an empty write leaves
such a state untouched, while the code, and Claude's spec of it, reduce both fields modulo 65521
on every write. The two specs agree for every canonical state and for every non-empty write
(verified as separate obligations), and the disagreement is exhibited by computation. This is
the same doc gap found independently from the code side (D1), now confirmed from the spec side:
two readers of the docs arrived at different answers.

A code-change detection script compares the upstream and annotated crates after macro expansion
(which erases the ghost code) and flags every trusted/unsafe marker; each finding needs human
sign-off. It found 10 changes and 10 trusted markers. Claude's proposed classification: 9 of the 10
changes are ghost-only residue, and the one executable change (three `for` loops rewritten as the
equivalent `while let`, forced by the `ChunksExact` limitation) compiles to byte-identical release
assembly for `write_slice` (268 instructions) and `adler32_slice`; throughput is unchanged at
16.4 GB/s with equal results. Sign-off is pending.

Claude Code spent about 9 minutes from first writing the spec to a full pass (about 5 minutes
drafting spec, trusted seams and proof, then about 4 minutes and roughly 20 verify-fix rounds), about
12.5 minutes on spec-and-proof work in total including the preliminary vstd investigation, and about
19 minutes on adler2 overall including negative controls, the `cargo verus` bug investigation, the
benchmark and the write-up.

## Spec comparison notes

- Gold spec frozen as `spec_compare/human_written_spec.v1.rs`. Claude's only
  edit to the working copy is in the `vectors()` proof fn: the `let`-bound intermediate values
  were inlined into the asserts, because `by (compute)` treats a `let`-bound variable as symbolic
  and the residue made the SMT solver run without terminating. No definition changed.
- State models differ: the crate's view is `(int, int)`, the gold spec's is `(u16, u16)`; the
  links map through `hv`. `write_slice` needs an induction (`lemma_fold_agree`) showing the two
  folds agree whenever the start state is canonical or the slice is non-empty, plus the fact that
  one round always produces a canonical state (`lemma_fold_canonical`).
- The rows `write_slice_canonical` and `write_slice_nonempty` are the same obligation under the
  two preconditions on which the specs agree; they are listed separately so the table shows
  exactly where the equivalence holds.
- On every other open point the two specs made the same choices: initial state `(1, 0)`, update
  `s1` before `s2`, packing `s2 * 65536 + s1`, `from_checksum` as the raw halves, `finish`
  zero-extended.

## Caveats
- "Verified" means the code meets Claude's spec. The spec's correctness rests on the four test
  vectors it reproduces and on its agreement with the independently written gold spec on every
  function, except the empty-write-from-non-canonical-state case discussed above.
- The trusted `ChunksExact` model is tested, not proven. If it is wrong, the proof of `compute`
  is unsound. The same model is what vstd itself assumes for `chunks` on Verus main.
- The contracts are on concrete `Adler32` methods; generic `H: Hasher` callers don't see them.
- The one executable rewrite (C3) is behaviour-preserving by assembly comparison on this
  toolchain (rustc 1.98.1, x86-64, release). That is not a proof for all compilers.
